# isoftstone-debug-recovery：Bug 修复编排

输入：`问题描述`（必填）、`前端代码路径`（选填）、`后端代码路径`（选填）。

## 严格约束（全程有效）

1. 缺信息就问，不猜：问题描述缺失、路径不存在、单双端判定不确定时，停下询问用户
2. 方案未经用户确认，不得修改任何代码
3. 修改范围以已确认方案为边界；review 基线 = 已确认方案
4. review 连续 2 轮不通过 → 汇报阻塞点，请用户决策
5. 前端/后端 subagent 必须在各自仓库目录下工作，自动遵循该仓库 CLAUDE.md 与规范

## 第 0 步：参数解析

1. 路径识别：以 `/` 或 `~` 开头、且用 `ls` 验证真实存在的目录 → 视为前端或后端代码路径（按用户标注或语义归类）
2. 其余自由文本 → 问题描述
3. 问题描述为空 → 追问用户，继续前不得进入第 1 步
4. 路径不存在 → 报错并要求用户更正
5. 创建 `<当前目录>/.debug-recovery/<问题slug>/` 目录，写入 `issue.md`：问题描述、参数；判定结论与确认后的方案随后续步骤追加。slug 由问题描述生成（kebab-case，不超过 40 字符，保证目录名合法）

## 第 1 步：单端/双端判定

按优先级依次判断，结论写入 issue.md：

1. 前后端路径都提供，或问题描述涉及接口调用链、跨端数据流 → **双端问题**
2. 只提供一个仓库路径 → 该端**单端问题**；若问题描述明显指向另一端 → 向用户确认
3. 无路径 → 关键词推断：
   - 页面、组件、渲染、样式、交互 → 前端
   - 接口、SQL、服务、事务、数据 → 后端
   - 无法推断 → 询问用户

## 第 2 步：分析

遵循 `agent-skills:debugging-and-error-recovery` 流程：复现 → 定位 → 根因。

- 单端：在该端仓库内分析
- 双端：分析跨端链路（接口契约、数据流），产出**前后端联合方案**，必须包含：
  1. 后端改动点
  2. 接口契约变更（若有：路径、方法、请求/响应字段变化；无变更写"无"）
  3. 前端适配点
  4. 执行顺序（接口变更场景固定：先后端再前端）

## 第 3 步：用户确认

向用户呈现：根因、修改点、影响面（双端含上述四要素）。

- 用户拒绝 → 带用户反馈回到第 2 步重新分析
- 用户确认 → 方案写入 issue.md，进入第 4 步（按第 1 步判定结果走 A 或 B）

## 第 4 步 A：单端执行

主会话直接修改，不派 subagent：

1. 实施修改
2. 调用 `superpowers:requesting-code-review` 审查。审查上下文附：原始问题 + 已确认方案 + 完整 diff；审查点：
   - 修改是否准确解决问题
   - 是否超出方案范围
   - 是否符合仓库规范
3. 不通过 → 按审查意见修复后重新审查（最多 2 轮，超限按严格约束第 4 条处理）
4. 通过 → 汇报结果与建议验证方式（运行/测试命令）

## 第 4 步 B：双端执行

主会话为 Lead，负责编排；确认方案后立即用 TaskCreate 建任务列表：

| 任务 | 描述要点 | 依赖 |
|------|----------|------|
| T1 后端修改 | 方案后端部分；遵循后端仓库 CLAUDE.md 与规范；完成后按下方模板写 blackboard.md；跑仓库测试/构建自验 | — |
| T2 后端 code review | 基线=已确认方案，审查准确性/范围/规范 | T1 |
| T3 前端修改 | 方案前端部分；附后端黑板交接记录；遵循前端仓库规则 | T2 |
| T4 前端 code review | 基线=前端方案+后端契约变更 | T3 |

执行顺序（接口变更场景：先后端再前端）：

1. 派发**后端 subagent**（general-purpose，工作目录=后端仓库）：修改 → 测试/构建自验 → 写黑板 → 返回报告
2. 主会话派发 review subagent（`superpowers:requesting-code-review` 流程）审查后端改动
3. 通过 → 标记 T1、T2 completed → 读 blackboard.md，交接记录注入 T3 任务描述 → 派发**前端 subagent**（general-purpose，工作目录=前端仓库）
4. 前端 subagent 完成 → 前端 review
5. 全部通过 → 标记 T3、T4 completed → 汇总报告：根因、两端修改摘要、黑板文件路径、建议联调验证步骤

subagent 完成会自动通知主会话，无需轮询。TaskList 表达状态，黑板表达交接内容。

### 黑板文件

`<当前目录>/.debug-recovery/<问题slug>/blackboard.md`，后端 subagent 按此模板写入：

```markdown
# 黑板：<问题slug>

## 状态
backend-in-progress | backend-done | backend-done-review-passed | frontend-in-progress | done

（backend-in-progress 由后端 subagent 写入；修改自验完成后更新为 backend-done；
review 通过后由主会话更新为 backend-done-review-passed；review 不通过则回到
backend-in-progress 继续修复。frontend-in-progress 由主会话派发前端任务时写入，
前端 review 通过后由主会话更新为 done。）

## 接口契约变更
（前端适配的权威依据；无变更写"无"）
- 接口：<路径 + 方法>
- 请求字段变化：
- 响应字段变化：

## 修改文件清单
- <文件路径>：<改动摘要>

## 前端适配要点
- <具体指导>

## 注意事项
- <边界、风险、回归点>
```

## 第 5 步：错误处理

| 场景 | 处理 |
|------|------|
| 问题描述缺失 / 路径不存在 / 判定不确定 | 停下询问用户，不猜 |
| 方案被用户拒绝 | 带反馈重新分析，不强行修改 |
| review 连续 2 轮不通过 | 汇报阻塞点，请用户决策 |
| subagent 失败 | 黑板保留现场，汇报状态，询问是否重试 |
| 黑板目录无写权限 | 降级为任务描述直接携带契约内容（不落盘） |
